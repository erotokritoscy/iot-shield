# Corpora: labelled data

A corpus is what the evaluation harness runs on: raw input text a run would ingest, plus an
answer key saying where the faults really were. This guide covers the on-disk format, the
synthetic generator that produces most of it, and how to add either.

Read `docs/guide/evaluation.md` first. This guide assumes you know what an incident is, why
truth is indexed by (asset, lane, instant), and what the roster means.

## Three tiers, for one reason: licensing

The harness gets its data three ways, and which one you use is decided by whether we may ship
the bytes.

| Tier | Command | Committed? |
|---|---|---|
| **synthetic** (`synthetic`, `fleet_scan`, `device_trimodal`, `meter_fleet`) | `eval generate` | yes, 701 KB |
| **converted** (`skab_valve1`, `skab_valve2`, `skab_clean`) | `eval fetch skab` | no, gitignored |
| **bring your own** | drop a directory in | yours |

SKAB, the Skoltech Anomaly Benchmark, is where every measured result in ADR-0021 came from,
and it is **GPLv3**: copyleft, with share-alike obligations on derivative works. This
repository declares no licence and its stated direction is a commercial product, so committing
SKAB's bytes, or even our labels derived from its `anomaly` column, would bake a licensing
question into git history where it is expensive to undo. So it ships as a conversion step.

That constraint is the whole reason the generator exists. Without something to replace SKAB, a
researcher who clones this repository gets a harness with one tiny corpus, which is a demo
rather than a benchmark. Generation solves it completely, because **the faults we inject are
the labels**: no annotation step, no third-party data, no licence question.

Obtaining SKAB is deliberately not automated. A silent network download into a research
repository is the kind of convenience that later turns out to have fetched something nobody
reviewed, so you name a local checkout and the URL is printed when the path is missing:

```
uv run python -m iotshield.eval fetch skab --source ../reference/.../Datasets/SKAB
```

## The bundle format

A bundle is a self-describing directory. Nothing else is required, and no code registers it:

```
data/eval/<corpus>/
  manifest.json                    name, description, provenance, licence, the case list
  cases/<case>.<ext>.gz            readings, in a format one of our normalizers parses
  cases/<case>.labels.json.gz      the answer key
```

**Discovered, not registered.** Corpora used to be Python loader functions in a registry, so
adding a dataset meant writing code. Scanning a directory means adding a corpus is *adding
data*, the same drop-in gesture as adding a config, and one a researcher can do without
reading our source. The CLI, the API and the dashboard all see a new corpus with no change to
any of them.

The root is `data/eval/`, overridable by `IOTSHIELD_CORPUS_PATH`. It is never a
caller-supplied value, because a request that names a path is a request to read arbitrary
files.

### The manifest

```json
{
  "name": "device_trimodal",
  "description": "One device observed on telemetry, syslog and flow at once: ... (3 recordings, 3 device(s), 3 injected fault(s))",
  "provenance": "iotshield.eval.generate - synthetic, reproducible from the seed",
  "licence": "CC0-1.0 (generated by iotshield; no third-party data)",
  "cases": [
    {
      "name": "compromise",
      "inputs": [
        {"source_format": "stub-csv",  "path": "cases/compromise.csv.gz"},
        {"source_format": "syslog",    "path": "cases/compromise-1.log.gz"},
        {"source_format": "flow-csv",  "path": "cases/compromise-2.csv.gz"}
      ],
      "labels": "cases/compromise.labels.json.gz"
    }
  ]
}
```

`provenance` and `licence` are **required**, not optional. The first problem this format had to
solve was which datasets we may redistribute at all, and a bundle that cannot say where it came
from is a bundle nobody can safely reuse.

`inputs` aligns positionally with a spec's `sources`, which is what makes the pairing table in
`eval list` derivable rather than declared.

### Readings stay in a real ingest format

A bundle holds the text a run would actually ingest, not a pre-parsed matrix. That is what
makes a benchmark exercise normalization too, so it measures the *pipeline* rather than a
detector in isolation. Gzipped because the corpora are repetitive numeric text (measured 4.4x
on SKAB) and a repository is a bad place for megabytes that compress away.

The extension is a hint for humans reading `ls`; the manifest is authoritative.

### The answer key

```json
{
  "schema_version": 5,
  "assets": [
    {"asset_id": "10.0.0.11", "clocks": {...}, "incidents": []},
    {"asset_id": "10.0.0.24",
     "clocks": {"flow": [...69 instants...], "log": [...26...], "telemetry": [...180...]},
     "incidents": [
       {"lane": "flow",      "kind": "compromise", "fault_id": "10.0.0.24:compromise:400",
        "spans": [["2026-01-01T00:06:40Z", "2026-01-01T00:07:18Z"]]},
       {"lane": "log",       "kind": "compromise", "fault_id": "10.0.0.24:compromise:400",
        "spans": [["2026-01-01T00:06:40Z", "2026-01-01T00:07:14Z"]]},
       {"lane": "telemetry", "kind": "compromise", "fault_id": "10.0.0.24:compromise:400",
        "spans": [["2026-01-01T00:06:40Z", "2026-01-01T00:07:15Z"]]}
     ]},
    {"asset_id": "10.0.0.53", "clocks": {...}, "incidents": []}
  ]
}
```

That is one real case, and almost every design decision from the evaluation guide is visible in
it.

**One fault, three incidents, one `fault_id`.** The camera's compromise is a single cause with
three observable projections, and their extents genuinely differ: flow ends at 00:07:18, log at
00:07:14, telemetry at 00:07:15. Nobody typed those. Each is the last instant that lane's
output actually differed from an unfaulted world.

**Clocks are per asset and per lane, and the numbers are wildly different.** The camera is
observed at 69 flow instants, 26 log instants and 180 telemetry instants. The gateway in the
same recording has 300 flow instants and 15 log ones. Pool those into one clock and the fastest
lane owns every metric.

**Two assets with `incidents: []` are asserted clean.** That is not missing data; it is the
corpus stating that a detection on the gateway or the mirror is an unambiguous false alarm. An
asset that is simply out of scope is *omitted from the file entirely*.

**Instants, not rows.** A clock entry is one moment this asset was observed at on this lane, not
one line of readings. Our contract fans a multi-channel reading into one event per channel, so a
1,148-instant SKAB recording is 9,184 lines of stub CSV.

Storing the clock alongside the intervals costs a little duplication and buys a labels file that
is a complete answer key on its own: the reader never has to parse readings to learn the truth,
so it needs no knowledge of their format.

The labels are gzipped like the readings, and for a sharper reason: the clock is a long run of
near-identical ISO-8601 strings, which is the best case for gzip and the worst case for storing
raw. Measured on the synthetic corpus, uncompressed labels were *larger* than the compressed
readings they annotate (264 KB against 220 KB). Read one with `gzip -dc`.

### Schema v5, and why old files are refused

The version history is one coordinate system being completed one axis at a time:

| | |
|---|---|
| v1 | one global clock, bare `(start, end)` pairs. "Something was wrong at 00:05." |
| v2 | the **asset** axis. "The camera was wrong at 00:05." |
| v3 | the **lane** axis, on the clock. "The camera's network was wrong." |
| v4 | the lane axis on the **incident**, so no field is read two ways |
| v5 | an incident's extent is a **list of spans**, so it is a projection not a run |

An older file is rejected with the command to regenerate, never upgraded:

```
BundleError: .../spike-0.labels.json.gz is a v4 answer key; this build reads v5, in which an
incident carries the list of spans its fault actually showed at rather than one interval per
contiguous run. regenerate it: `python -m iotshield.eval generate` for a synthetic corpus,
`python -m iotshield.eval fetch <dataset>` for a converted one
```

For v1 through v3 that is forced: an upgrade would have to invent the missing dimension, and
the only place to find it is the readings, which is precisely what this format exists to avoid
needing.

**v4 is the interesting exception.** A v4 incident is a v5 incident with one span, so it is
mechanically upgradable. It is still refused, because the upgrade would be **lossless but
wrong**: v4 wrote one row per contiguous run, so re-reading those rows as one-span projections
would preserve exactly the inflated denominator v5 exists to remove, and do it silently.
Regenerating re-derives the grouping from the fault ids the generator knew all along.

The version is read *structurally*, before shape validation, exactly as the detector artifact
loader does and for the same reason: `extra="forbid"` would otherwise reject a v1 payload with a
pydantic complaint about an unexpected `timestamps` key, which tells the reader nothing about
what to do.

### A bundle is untrusted data

That is the premise of "discovered, not registered": corpora are a drop-in a third party
supplies, `data/eval` is a bind mount in compose, and the eval API loads whatever is under the
corpus root. So every manifest path is resolved through one function that refuses anything
escaping the bundle:

```
BundleError: manifest path '../secret.txt' resolves outside its bundle (...); a bundle may
only reference files it contains
```

An absolute path is refused the same way. Without it, a manifest was a way to read any file the
server can and return its contents inside a benchmark report. `resolve` comes first, because
the traversal may be spelled with symlinks or `..` segments that only normalize away on a real
path.

`BundleError` subclasses `ValueError` deliberately. As a bare `RuntimeError` it was caught by
*nothing*: the CLI and the API both map `ValueError`, the listing functions swallowed it into a
`continue`, so a bundle with a stale answer key was listed normally and then raised uncaught
when selected, and every carefully worded message in the module was unreachable.

### One input shape per corpus

A benchmark checks each case's inputs against *one* spec positionally, so a corpus whose cases
disagree is unbenchmarkable by construction:

```
BundleError: corpus 'device_trimodal' mixes input shapes (stub-csv, syslog / stub-csv, syslog,
flow-csv); every case must supply the same formats in the same order, or no single spec can
benchmark it
```

Checked at load rather than case by case mid-run, and it also lets a caller compose a matching
spec without decompressing any readings, which is what stops a picker offering a corpus it
cannot run.

## The generator

The rest of this guide is about `eval/generate/`, which produces the four committed corpora.

The first version of it fused three concerns in one function: what the world did, how it is
written down, and what the answer key says. That is why it could only ever produce single-asset
telemetry, since every extension hit all three at once. They are now separate:

| Module | Holds |
|---|---|
| `world.py` | devices, a clock, declared faults. No formats, no channels, no IPs. |
| `port.py` | `Behaviour` (one (lane, payload) shape's normal plus what a fault does to it) and `Renderer` (events to wire text) |
| `build.py` | simulate, render, and **derive** the answer key from what was expressed |
| `rng.py` | one private random stream per thing, so the corpus can grow |
| `faults.py` | a fault is a name; which lanes show it is derived |
| `scenarios.py` | the shipped corpora, as data |
| `telemetry.py`, `syslog.py`, `flow.py`, `meter.py` | one behaviour and its renderers per shape — `meter.py` is a *second* telemetry-lane behaviour, which is why the registry is keyed on both axes |

### A recording is a small world, not a file

That reframing is what the package is built on. The old generator treated a labelled recording
as *a file of numbers with a fault in it*, which describes a single sensor on a single rig and
nothing else: a network capture is many devices talking to each other, and a multimodal
recording is three files describing the same fifteen minutes.

So a recording is some devices, over some stretch of time, some of which go wrong. Files are a
*rendering* of that world, and the answer key is *derived* from the declared faults. Multimodal
is not a special case: `Scenario.formats` is a tuple, and a single-lane corpus is the one where
it has one element.

```python
Recording(
    name="compromise",
    clock=Clock(steps=900, step=timedelta(seconds=1)),
    devices=(camera, gateway, mirror),
    faults=(FaultSpec(kind="compromise", asset_id=CAMERA,
                      start_step=400, length_steps=40, intensity=1.3),),
)
```

`Device.kind` selects a *profile* within a behaviour, so a fleet of cameras and gateways needs
one network behaviour rather than one per device type. `Device.role` is read by no machinery at
all, deliberately: it labels *why* a device is in a scenario ("inbound-heavy jump host") at the
point where a reader is deciding what the scenario proves. A comment cannot be attached to one
element of a tuple, which is what makes a field the right home for it.

### Nothing annotates anything

The step that makes the whole approach work is the last one. The faults were declared in the
world, the behaviours report **which instants they actually perturbed**, and the labels are
read off those instants. The answer key cannot disagree with the data, because it is made of
the data.

That was an aspiration for a while, and the gap is instructive. Behaviours used to report a
bare fault id, set when a handler was *dispatched* rather than when the output changed, and the
interval was recomputed in the builder from the declared `FaultSpec` window. Two computations
of one interval, only one of which had touched a byte. So:

- a fault of `intensity=0.0` produced byte-identical output and still shipped labelled;
- a fault clamped into range by a handler was labelled at its *unclamped* declared window, an
  unwinnable recall miss no detector could ever score against.

`Observed.expressed` now maps each `FaultSpec` to the set of instants at which that lane's
output differs from the unfaulted world. Every behaviour already computed this at the line where
it used to discard it.

A behaviour with no vocabulary for a fault reports nothing for it, and that is not a gap: a
compromised camera really does still read 22 degrees. The answer key records which modalities
carried the signal, and when, because the generator *observed* it.

`expressed` is keyed by the `FaultSpec` object rather than by `fault_id`, because that id is a
readable display string (`asset:kind:start_step`) and two faults sharing one would silently
merge into a single label. `FaultSpec` is frozen and therefore hashes by value, which
distinguishes two faults differing in *any* field, including an intensity a shared display id
would hide.

### One dimensionless intensity

`FaultSpec.intensity` is a single scalar, and it is **multiples of the detector boundary for
that fault kind**. `1.0` means "exactly at the alarm line" on every lane at once, and each
behaviour converts it into its own units by multiplying the `Calibration` it declares: 20 peers
for a fan-out, 15 ports for a port sweep, 50 MB for an exfiltration, 5 lines for a log storm, a
value of 80 for the telemetry threshold, and 3x an hour-of-week expectation for a meter.

A single scalar was always right; leaving it **dimensioned** was not. The same number used to
mean "30 peers" to the flow behaviour and "multiply the thermal rise by 30" to the sensor rig.
So the trimodal compromise, documented as deliberately *marginal* precisely so the corroboration
A/B would measure corroboration rather than an obvious spike, drove the camera's temperature to
316.7 degrees against a threshold of 80, and the telemetry-only arm caught it outright. The
experiment was comparing corroboration against an already-solved problem, and nothing could see
it.

Note that the boundary is not a *trip*: the Detector port mandates a strict `>`, so `1.0` sits
exactly on the line and a fault meant to fire needs a little more. That asymmetry belongs to the
detector.

A boundary is declared per *fault kind*, not per behaviour, because fan-out's 20 peers and the
port scan's 15 ports are different alarm lines on one lane.

A boundary may also name **no** registry parameter, and only then (ADR-0038 D5). `meter_iforest`
fits its threshold to a false-alarm budget on each meter's own history, so there is no default
for `intensity=1.0` to equal, and `fp_budget` cannot stand in for one — a rate is not a
magnitude. Its boundary is quoted in units the behaviour owns, and the registry check below is
replaced by a behavioural one: the scenario asserts the fault is actually caught at the declared
intensity, which is the only way to validate a number in a behaviour's own units. The hatch is
narrowed to `Fittable` detectors by a meta-test, so it cannot become the easy way out.

### The two extension points

A **Behaviour** models one lane's normal, expresses the faults aimed at a device, and reports
what it perturbed. It produces `NormalizedEvent`s, which is the right currency because that
contract genuinely carries all three lanes: `severity` for a log line, `metadata` for a flow
record, `metric`/`value` for a sensor reading.

A **Renderer** turns those events into wire text. It is worth its own object for two reasons.

It makes rendering the formal **inverse of a normalizer**, which is checkable: emit the text,
run it through the *real* normalizer, and confirm you get back what you claimed to write. A
renderer that lies about its lane, writes a timestamp that will not parse, or names a device the
normalizer re-attributes to the peer fails that test immediately.

And dialect multiplicity is measured, not speculative: seven wire formats already exist across
three lanes, two of them dialects of metering — a second *shape* on a lane that already had one
rather than a fourth lane. "How a pump behaves" and "which dialect it is logged in" are
different questions, so adding a dialect is a renderer and nothing else.

`LaneBehaviour` is the base every lane shares. A behaviour declares two tables keyed by fault
kind (what each fault does, and what boundary its magnitude is quoted against) and everything
else the Protocol asks for is derived from them. `expresses` is the handler table's keys, so a
fault a lane renders and one it *claims* to render cannot be different sets. The two tables are
checked against each other in the constructor, which is the part no lane can forget:

```
ValueError: LaneBehaviour expresses ['compromise', 'drift', 'spike', 'stuck'] but declares
boundaries for ['drift', 'spike', 'stuck']; every fault a lane can show must say what its
magnitude is measured against
```

The four shipped behaviours, for reference, with `compromise` appearing in three of them because
that is what makes a trimodal corpus possible — and two of them sharing the telemetry lane,
which is the whole reason `BEHAVIOURS` is keyed on `(lane, payload)` rather than on lane alone
(ADR-0035): a meter is a different vocabulary inside a modality that already had one.

```
telemetry          SensorRig    compromise, drift, spike, stuck
telemetry / meter  MeterFleet   drift, spike, stuck
log                LogSource    auth_storm, compromise, error_storm
flow               NetworkHost  compromise, exfiltration, port_sweep, scan
```

Before that base existed, `expresses` was `frozenset(self._handlers)` in three files,
`calibration` was a hand-typed tuple in two of them, and a meta-test checked that the
hand-written value still matched the boundaries it was supposed to be derived from. A test whose
whole job is to re-establish a law the code could have made true by construction is the
signature of a mechanism sitting one level too low.

### A fault owns no rendering

`FAULTS` is a name and a description. That is all.

The tempting design is for a fault to know how to damage each modality, and the cost of that is
fatal to extensibility: adding a fourth lane would mean going back and teaching *every existing
fault* how to express itself in it. So the direction is inverted. Each behaviour decides what a
fault name looks like in its own world by putting it in its handler table, and `lanes_of` asks
the behaviours rather than storing the answer.

The nine shipped shapes are chosen to **discriminate**, which is the point of a corpus. A corpus
where every detector scores the same teaches nothing:

| Shape | Discriminates |
|---|---|
| `spike`, `drift` | caught by a fixed threshold |
| `stuck` | frozen at a plausible value, in range throughout: a fixed threshold is structurally blind |
| `scan` | many distinct peers, one port |
| `port_sweep` | many ports, few peers, so fan-out cannot see it |
| `exfiltration` | bulk to one peer: neither cardinality shape sees it |
| `error_storm` | a burst of error-and-above lines |
| `auth_storm` | the same burst at INFO, invisible to a severity floor |
| `compromise` | expressed by all three behaviours: the reason a trimodal corpus can exist |

### Determinism that survives growth

A committed corpus must be **fixed**, or every benchmark silently measures a different dataset
and no two results are comparable.

The obvious way to get that is one seed per recording, drawing values in order. It works, and it
makes the corpus **ungrowable**: because the draws are sequential, inserting a device (or even a
channel) shifts every value after it, so adding one device rewrites the whole corpus and
invalidates every number already measured on it. The old generator had exactly that shape.

So no stream is shared. Each is derived from its own *name*: this scenario, this recording, this
device, this lane, this purpose.

| Change | What moves |
|---|---|
| add a device to a recording | only that device's lines |
| add a lane to a scenario | only that lane's payload file |
| add a recording | only that recording's files |
| reorder the devices in a recording | nothing (the builder sorts before rendering) |
| rename a device | that device's lines (a rename *is* a new device) |

The lane-scoping pays off twice: it is what lets one recording be rendered as one lane in one
bundle and as three in another with the shared lane's payload **byte-identical**, which makes a
corroboration A/B apples-to-apples by construction rather than by hope. Note lane, not format:
re-rendering in a second dialect of the same lane describes the same world, or a dialect-parity
test could never be written.

Never `hash()`. Python randomizes string hashing per process unless `PYTHONHASHSEED` is pinned,
so a seed derived from it would produce different data on every run, silently. The names go
through `blake2b` into a `SeedSequence`, so two names differing in one character give unrelated
streams rather than adjacent ones. There is a test for exactly the `PYTHONHASHSEED` case.

Reproducibility is verified, not asserted. `test_a_fresh_build_reproduces_the_committed_bytes`
rebuilds each bundle and compares every file byte for byte, and a fresh regenerate today matches
all 56 committed files:

```
synthetic:       23 files, differing: none
fleet_scan:      11 files, differing: none
device_trimodal: 13 files, differing: none
meter_fleet:      9 files, differing: none
committed size: 701 KB          (budget: 4 MB)
```

That property is not decorative. The demo rebuild of 2026-07-30 deleted `data/eval/` outright
and regenerated it; `git diff` on the directory came back empty, which is what made it safe to
keep every corpus-derived number in the README unchanged while every demo-derived one had to be
re-measured.

Two platform leaks had to be closed to make that true, and both are worth knowing because they
are invisible until a byte-equality test exists.

**Line endings.** `write_text` with the default `newline=None` translates to `os.linesep`, so a
bundle generated on Windows carried CRLF while `.gitattributes` checks the file out with LF. The
freshness test then failed on a fresh Windows clone for a reason that has nothing to do with the
corpus, and passed only where a previous local build had already overwritten the file. Every
bundle text file is written with an explicit `\n`.

**The gzip OS byte.** The same problem one layer down: the platform leaking in through the
*container* rather than through text encoding. RFC 1952 puts an OS byte at offset 9, no
decompressor ever reads it back, and a byte-equality test does. `gzip.compress(..., mtime=0)` is
asked for precisely because it is reproducible, and on CPython 3.12 and earlier that argument
selects the one path that is not: it hands the whole header to zlib, which stamps its own
compile-time OS code (3 on Unix, 10 on Windows). 3.13 deleted the shortcut and writes 255
("unknown"). So a corpus generated on 3.13 and rebuilt on 3.12 differed by one informationless
byte per file, with a byte-identical deflate stream, and that is exactly how the test failed on
CI (Python 3.12.3) while passing on a developer machine (3.13). The byte is now forced to 255,
which makes a bundle's bytes a property of the *format* rather than of whichever interpreter
wrote them.

### Device profiles, so a corpus is not owned by its fastest device

`Device.kind` selects a profile inside a behaviour. On telemetry that is the channel set and the
sampling rate:

```python
"sensor":  channels=_RIG                                          # the rig's 3 process channels, 1 Hz
"camera":  {"Temperature": (62.0, 0.9), "FrameRate": (25.0, 0.4)}, every_steps=5
"gateway": {"CpuLoad": (38.0, 3.0), "Temperature": (58.0, 1.2)},   every_steps=30
```

A network appliance therefore stops emitting industrial pressure readings at 1 Hz, and stops
contributing 900 instants to a corpus alongside devices that report twice a minute. Before that,
one device kind dominated every pooled point metric by sheer row count.

On flow the profile is normal traffic, and the four standing devices in `fleet_scan` are not
scenery. Each is a **control** that the flow detector's presets make a claim about and that had
never been measured:

| Device | Control |
|---|---|
| `10.0.0.11` gateway | 20 flows per minute to **one** destination: volume is not fan-out |
| `10.0.0.9` server | dialled *into* by many peers: inbound is not fan-out |
| `10.0.0.1` resolver | legitimately chatty, sitting just **under** the 20-peer boundary |
| `10.0.0.53` mirror | legitimately chatty **above** it, so the corpus measures what a fleet-wide constant costs |

That last one is the interesting one: ADR-0024 predicted that false alarm in its Consequences,
and here it becomes a number rather than a prediction.

## What generation refuses

Every one of these would produce a corpus that *looks* fine and scores wrong, so each is
refused while building rather than shipped. This is the list to read before writing a scenario.

**Two devices sharing an asset id.**

```
recording 'r' declares ['a'] more than once; an asset id names exactly one device, because it
selects that device's profile and is the key its faults, its clock and its roster entry are all
looked up by
```

The damage was silent and large. Both devices were handed the *same* `FaultSpec`, both reported
perturbed instants under it, and the builder's merge kept only the last writer. Measured on a
rig and a camera sharing an id: the rig's 118 perturbed instants were discarded and the camera's
22 survived, which, being sparse against the rig's 900-instant clock, split into **22
single-instant incidents** where the corpus should have had one. No error, no warning, an answer
key off by a factor of twenty-two.

**Two faults colliding on `fault_id`.** The id is `(asset, kind, start_step)` and ignores length
and intensity, so two faults differing only in those would merge into one incident.

**A recording with no devices**, a fault aimed at a device that is not there, and a device that
emitted nothing on any recorded lane. The last one matters because findings on an unlisted asset
are *unscoreable* rather than false alarms.

**A negative intensity.** It used to reach the telemetry handlers as a negative amplitude and
drive a rig's pressure to -160 while the answer key still called it a spike, while the flow and
log lanes hid it entirely because their unit conversion floors at one record. Two different
wrong answers to one meaningless input.

**A fault starting at or after the end of the clock.** Only the lower bound was checked, and the
lanes disagree about what an out-of-range start means: telemetry *clamps* to the last sample
while the additive lanes keep counting past the end. One declared fault produced projections over
an hour apart on different lanes, sharing a `fault_id`, so cross-lane correlation, the entire
point of a trimodal corpus, could never fire. Refused rather than clamped, because clamping is
what made them disagree.

**A fault no recorded lane can express.**

```
case 'r': no lane in ['stub-csv'] expressed ['rig:scan:10']. A label nothing can see is
unfindable by construction, and would drag recall down for a reason no reader could diagnose
```

This only became load-bearing once `expressed` carried instants. While it held fault ids set on
handler dispatch, it could not distinguish "this lane models this fault" from "this lane's
output changed", so a fault that perturbed nothing passed it.

**An intensity that would invert the fault**, with the remedy computed:

```
fault 'rig:spike:10' declares intensity 0.0 on channel 'Pressure', whose baseline is 45.0
against a boundary of 80.0. That asks for a rise of -45.0: the fault would run downward while
still being labelled 'spike'. The lowest intensity that raises this channel is 0.562
```

**Two dialects of one lane in one scenario**, which is the subtlest of them:

```
scenario 'x' records 'flow-csv' and 'zeek-conn', which are both flow formats. A run pools its
sources into lanes, so every flow event would reach the detectors twice while the answer key
counted it once; compare dialects as two corpora instead
```

Positionally the corpus is valid and both inputs parse. What breaks is one joint later: a run
pools its sources into lanes, so peer counts, byte totals and burst counts all silently double.
The answer key does *not* double, because a clock is a set of instants and duplicate timestamps
collapse. That asymmetry is what makes it invisible.

**An asset id its own renderer mangles.**

```
recording 'r' rendered as syslog reads back as device(s) ['Pump'], which it never declared - an
asset id must survive its own renderer, or the answer key names a device absent from the data
```

`Device(asset_id="Pump 3")` on syslog renders and validates cleanly, and the pipeline attributes
those events to `"Pump"`, because the HOST field is space-delimited. The roster and every
`fault_id` then name a device that appears nowhere in the data, recall on it is structurally zero
forever, and every detection lands in `unlabelled_detections` with nothing saying why. The check
round-trips through the **actual normalizer**, which is what makes it unable to rot: a character
policy per renderer would have to be re-derived whenever a dialect changed a delimiter.

## Adding a corpus, end to end

This is the thing you are most likely to do, and "adding a corpus is adding a `Scenario`" is easy
to write and easy to disbelieve, so here is the whole of it with nothing skipped. Everything below
was run; the numbers and the transcripts are what came back.

**None of it is committed.** `log_presets` is not in `data/eval/`, and the two bench specs
below are not in `config/bench/` - they are files you write as you follow this. What is being
shown is the *cost* of adding a corpus, and shipping a corpus nothing else measures against
would teach the opposite lesson. Write the four files and every transcript here reproduces.

**The gap being filled.** `log_burst` ships two presets that ask the same question of different
lines: `severity_spike` counts records at ERROR and above, `auth_failure` matches on the *message*
because sshd logs a failed password at INFO. The claim implied by shipping both is that each is
blind to the other's shape. Nothing measures it. The log lane appears in `device_trimodal` only as
a decoy, and `synthetic` and `fleet_scan` are telemetry and flow. So: a log-only corpus with one
storm of each kind, on two different devices.

### 1. Write the scenario

The whole change to the product is this block appended to
`src/iotshield/eval/generate/scenarios.py`, plus its name in the `SCENARIOS` dict at the bottom.

```python
CLOCK = Clock()
FLEET = (
    Device(asset_id="gw-1", kind="gateway", role="uplink"),
    Device(asset_id="cam-1", kind="camera", role="IP camera"),
)

LOG_PRESETS = Scenario(
    name="log_presets",
    description="Two log burst shapes on separate devices, plus a clean recording",
    formats=(SYSLOG,),
    recordings=(
        Recording(
            name="both-storms",
            clock=CLOCK,
            devices=FLEET,
            faults=(
                # 2.0x log_burst's min_count of 5 = 10 error lines, and 2.4x = 12 auth
                # failures. Neither number is written here; both are read off the boundary
                # the log behaviour declares.
                FaultSpec(kind="error_storm", asset_id="gw-1",
                          start_step=200, length_steps=40, intensity=2.0),
                FaultSpec(kind="auth_storm", asset_id="cam-1",
                          start_step=500, length_steps=40, intensity=2.4),
            ),
        ),
        Recording(name="clean", clock=CLOCK, devices=FLEET),
    ),
    seed=7000,
)
```

Four things are worth reading off it, because each is a rule from an earlier section arriving in
practice.

**Nothing here names a wire format except `formats`.** The scenario says syslog once, at the
scenario level, and the two devices know nothing about it. That is what makes the same recordings
renderable as a second dialect later without touching a line of this.

**No line counts appear anywhere.** `2.0` means "twice `log_burst`'s alarm line", and the log
behaviour turns that into ten lines because it declares `min_count` as its boundary. Write `10`
instead and the corpus silently stops discriminating the day somebody changes the preset.

**The clean recording is not padding.** It is the only place a false alarm can be counted, since
both devices are listed with `incidents: []` there, which is the asserted-clean state.

**The two devices exist so the storms are separable.** Put both faults on one device and a
detector that fires once looks identical to one that fires for the right reason.

### 2. Generate it

```
$ uv run python -m iotshield.eval generate log_presets
wrote data\eval\log_presets  (2 cases, 2 incidents)
```

Two incidents rather than four, because an incident is one (fault, lane) projection and both faults
show on one lane only.

### 3. It exists everywhere now, with no other change

```
$ uv run python -m iotshield.eval list
Corpora in ...\data\eval:
  log_presets        2 recording(s)  Two log burst shapes on separate devices, plus a clean
                                     recording (2 recordings, 2 device(s), 2 injected fault(s))
  ...

Corpora and the shipped specs that fit them:
  --corpus log_presets      --spec (none)
```

`eval list`, `/eval/corpora` and the dashboard's corpus picker all read the directory, so none of
them needed telling. Note the size phrase appended to the description: the count came from the
built corpus, not from the string typed above.

`--spec (none)` is the pairing table doing its job rather than a failure. No committed bench spec
declares a single syslog source, so none of them fits this corpus, and the table says so instead of
letting you discover it as a row of zeros.

### 4. Write the specs the corpus exists to compare

Two files identical but for one line, which is what makes the comparison an ablation rather than
two experiments. Neither is in the repository; write them where the command in step 5 looks for
them.

```yaml
# config/bench/log_severity.yaml   (write this; the other differs by the `preset:` line alone)
sources:
  - normalizer: syslog
    source_format: syslog
detectors:
  - name: log_burst
    params:
      preset: severity_spike        # ...or auth_failure, in the second file
alert_engine:
  name: weighted
```

One source, because `formats` has one entry: a bench spec declares one source per input position,
in the corpus's order.

### 5. Run the A/B

```
$ uv run python -m iotshield.eval --corpus log_presets \
      --spec config/bench/log_severity.yaml --spec config/bench/log_auth.yaml

corpus: log_presets - Two log burst shapes on separate devices, plus a clean recording (2 recordings, 2 device(s), 2 injected fault(s))
  2 case(s), 2 labelled incident(s)   fit protocol: none

spec            detectors      evF1     evP     evR   ovl    ptF1  det/inc  alt/inc   cover
log_severity    log_burst      0.67    1.00    0.50  1.00    0.62     0.50     0.50    0.50
log_auth        log_burst      0.67    1.00    0.50  1.00    0.71     0.50     0.50    0.50

--- log_severity - per case ---
case                      inc   det  alerts    evF1  det/inc  alt/inc   latency
both-storms                 2     1       1    0.67     0.50     0.50        0s
clean                       0     0       0       -        -        -         -
  * per-lane event recall: log=0.50
  * per-lane point precision/recall: log=P1.00/R0.45
```

The two rows are identical, and that is the finding rather than a disappointment: each preset
catches exactly one of the two storms, with perfect precision and perfect overlap, and misses the
other completely. The headline cannot show *which* one, so ask the timeline:

```
log_severity  detection window  00:03:20 -> 00:03:56     (gw-1, the error storm)
log_auth      detection window  00:08:20 -> 00:08:56     (cam-1, the auth storm)
```

Same corpus, same lane, same detector, opposite halves. `ovl 1.00` says each detection covered its
incident exactly, and `clean` scores zero detections on both arms, so neither preset bought its
recall with noise. The one number that does separate them, `ptF1` 0.62 against 0.71, is not a
quality difference: the auth storm is twelve lines to the error storm's ten, so there are more
faulty instants to be right about.

### 6. Pin the claim as a test

A corpus that measures something and asserts nothing will drift and take the whole benchmark with
it. The pattern to copy is `TestFleetScanDiscriminates` in `tests/eval/generate/test_scenarios.py`:
build the corpus, run the shipped spec over it once behind a `@cache`, and assert the claims the
corpus was built to make.

```python
def test_a_severity_floor_is_blind_to_an_auth_storm(self) -> None:
    # sshd logs a failed password at INFO, so a rule that counts ERROR-and-above
    # cannot see a brute force however long it runs.
    assert _log_cases("log_severity")["both-storms"].incidents_caught == 1

def test_neither_preset_alarms_on_the_clean_recording(self) -> None:
    # Guards both blindness claims above: "caught one of two" would read the same way
    # if the detector fired at random.
    assert _log_cases("log_severity")["clean"].alerts == 0
```

### What that cost

About forty lines of scenario, two eight-line YAML files, and a test class. No loader, no registry
function, no schema change, no API change, no dashboard change, and nothing in `eval/` that knows
the corpus exists. The meta-tests in `tests/eval/generate/` picked it up automatically, since they
are parametrized over `SCENARIOS`: it was checked for a licence, for one input per declared lane,
for carrying clean recordings as well as faulty ones, and for round-tripping through a bundle,
without any of those tests being edited.

The one thing generation will not catch for you is a fault too *weak* to find. It refuses a fault
that changed nothing, and `Calibration.units` floors a count at 1, so `intensity=0.0` still injects
one line: a real perturbation, correctly labelled, and invisible to any preset with a `min_count`
of 5. That is what the difficulty assertions in step 6 are for.

## Adding other things

**A wire dialect:** one `Renderer`, one line in the registry.

**A lane, or a second payload on an existing one:** one `Behaviour`, one `Renderer`, two
registry lines. No fault changes. The registry is keyed on the `(lane, payload)` pair, so a
metering behaviour sits beside the sensor rig on the telemetry lane rather than displacing it.

**A fault shape:** a `FAULTS` entry plus a handler and a boundary in each behaviour that should
show it.

**A third-party dataset:** a `Dataset` entry in `fetch.py` with a `convert` callable returning
`Corpus` objects. Let `AssetTruth.from_timeline` own the collapse of per-row flags into
incidents rather than re-deriving it, or the answer key gets a second definition of "one
incident".

Registration for behaviours and renderers happens in one place, `generate/__init__.py`, rather
than by import side effect in each module: a registry populated from six files is a registry
nobody can read, and an unimported adapter would be silently absent.

The meta-tests in `tests/eval/generate/` then hold the new thing to every law, and several of
them are *closure* checks rather than examples:

- every registered renderer and behaviour joins the suite;
- every behaviour's `(lane, payload)` shape has at least one renderer, and every renderer's
  shape has a behaviour — the pair, not the lane, which is what stops a meter dialect being
  handed the sensor rig's plain numeric readings;
- every benchmarkable format can be generated;
- every renderer's `source_format` is parsed by a registered normalizer, and its text round-trips;
- every registered fault is expressed by some lane, and every expressed fault is registered;
- every expressible fault has a boundary, and every declared boundary matches the detector
  parameter it names in the real registry — or, where it names none, belongs to a `Fittable`
  detector and is validated behaviourally instead.

That last one is the one that keeps a corpus honest over time. The telemetry corpus only
discriminates while its channel scales straddle `stub_threshold`'s default of 80. Change either
side and the corpus quietly stops teaching anything with the whole suite still green, because a
bench spec pins its own threshold and cannot see the drift.

## Edge cases and traps

**A corpus answers to its directory name *or* the `name` in its manifest.** They normally agree,
and accepting either means renaming a folder does not break a saved command line. What a
*listing* publishes, though, is the manifest name — so a directory called `stale` whose manifest
says `synthetic` appears as `synthetic` and is reachable under both, which is confusing rather
than dangerous. Keep them equal; the generator and the fetcher both do.

**A directory without a manifest is silently skipped, one *with* a broken manifest is not.** The
corpus root is a place people put things and one stray folder should not break a listing, but a
broken bundle is listed *with its reason* rather than hidden, so it is visibly broken instead of
absent from a picker.

**The builder owns ordering, renderers do not.** Every device's events for a lane are pooled and
sorted by `(timestamp, asset_id)` before rendering, so a multi-host capture is one time-ordered
file the way a real one is, and the normalizer's per-line statelessness gets exercised. A
renderer that sorted internally would fight that. `header()` is separate from `render()` for the
same reason: a CSV needs its column row once and Zeek needs its `#fields` directive once,
however many devices contribute.

**Streams are scoped by lane, not by source format.** Keying on the format would make a
behaviour's draws depend on which dialect rendered them, so the same scenario rendered as Zeek
would describe different traffic than one rendered as CSV.

**`Clock.spread` exists so a burst lands inside one sliding window** rather than piling onto a
single instant. It was open-coded four times across three modules, which is four chances for the
rule to drift.

**There is no `Clock.span`.** It computed a fault's interval from the *declared* window, which is
what let a label describe a stretch of time the data never showed anything at.

**`Incident` construction is keyword-only.** The previous shape relied on `asset_id` being
positionally first so a call written against an older signature would bind a datetime into an
asset field and fail loudly. That trick protects exactly one refactor, and a plain dataclass
performs no validation, so a mis-ordered positional call would have bound a `datetime` into
`lane` in silence.

**`Scenario.counts` is derived, not written.** The pre-rewrite generator computed it, the rewrite
briefly hard-coded it, and it immediately drifted: one scenario said "15-device fleet" while a
recording in it had 16 devices. The size phrase is appended to the description at build time.

**`fetch.py` imports the asset id from the detector trainer rather than retyping it.** A model is
filed under an asset id, so an id the SKAB bundles do not use makes the shipped artifact skip
every recording and report zeros. Nothing else would catch the drift: SKAB bundles are
gitignored, so an absent corpus is a CI *skip*, and the mismatch would surface only as an
unexplained empty benchmark.

**The trimodal decoys are load-bearing.** Corroboration multiplies an alert's priority; it never
creates or removes one. So the only metrics that can move in the A/B are the *ranking* ones, and
with one device and one incident the true alert is rank 1 in both arms and the corpus would pass
its own test while measuring nothing. The chatty mirror on flow and the log-storm gateway exist
so there is a queue to be re-ranked.
